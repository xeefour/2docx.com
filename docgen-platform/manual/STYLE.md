## 1 · ขอบเขต

ใช้กับ **3 ส่วนที่ใช้แบรนด์เดียวกัน** คือคู่มือที่ `/docs` · เว็บแอปที่ `apps/web` · หน้าวิเคราะห์ log ที่ `/analyze`

**ใช้กับทั้งสามส่วน** — โทเคนสี กติกาคอนทราสต์ กลไกโหมดมืด รูปร่างกล่อง ระยะห่าง ตัวอักษร

| | คู่มือ `/docs` | เว็บแอป `apps/web` | หน้า `/analyze` |

## 2 · สีหลัก

**เขียวเข้ม `#1d6f5c` (โหมดสว่าง) / `#5fbfa2` (โหมดมืด)**

เป็นสีเดียวที่ใช้ทำหน้าที่ "แบบย้ำ" ได้ทุกกรณี — ลิงก์ หัวข้อที่ active เลขลำดับขั้นตอน
กรอบกล่องข้อความประเภทข้อมูล สีเลือกของ checkbox และขอบเน้นของช่องค้นหา

ในโหมดมืดต้อง **สว่างขึ้น ไม่ใช่มืดลง** เพราะพื้นหลังมืดอยู่แล้ว
ถ้าเอา `#1d6f5c` ไปวางบนพื้นมืดจะจมหายไปทั้งก้อน เห็นเป็นสีเทาเข้ม

### 3.6 โทเคนที่มีเฉพาะเว็บแอป

เว็บแอปมีงานที่คู่มือไม่มี จึงต้องมีโทเคนเพิ่ม แต่หลักการเหมือนเดิมทุกประการ

| โทเคน | สว่าง | มืด | ใช้ทำอะไร |
|---|---|---|---|
| `--on-brand` | `#ffffff` | `#0f231d` | ตัวอักษรที่วาง**บนพื้น `--brand`** |

> ⚠️ `--on-brand` คือโทเคนที่ห้ามยกเว้น
>   ปุ่มหลักของเว็บใช้พื้น `--brand` และตัวอักษรต้อง**สลับขั้ว**ตามโหมด
>   ถ้าเขียน `color: #fff` ตายตัว ตอนโหมดมืดจะเป็นขาวบนเขียวอ่อน = อ่านไม่ออก
>   และจะไม่มี error ใด ๆ รายงาน
>
>   เคยพลาดตรงนี้จริง: กติกา `button { color: #fff }` ของโปรเจกต์ทำให้ปุ่มทุกปุ่ม
>   รับสีขาวไว้ ต่อมาต้องไล่กำหนด `color` ให้ทีละปุ่ม — กลายเป็นงานร้อยจุด
>   มีโทเคนเดียวจบ

#### แผนที่ชื่อโทเคนของเว็บแอป

| ในคู่มือ | ในเว็บแอป | ค่าเหมือนกัน |
|---|---|---|
| `--accent` / `--accent-soft` | `--brand` / `--brand-soft` | ใช่ |
| `--text` / `--text-dim` / `--text-faint` | `--ink` / `--ink-2` / `--ink-3` | ยกเว้น `--ink-3` ดูข้อ 4.3 |
| `--danger` / `--danger-soft` | `--err` / `--err-bg` | ใช่ |
| `--warn` (คู่มือไม่มีพื้น) | `--warn` / `--warn-bg` / `--warn-line` | — |
| — | `--on-brand` | มีเฉพาะเว็บ |
| — | `--shadow` `--shadow-md` `--shadow-lg` `--brand-glow` | มีเฉพาะเว็บ |
| — | `--veil` `--scrim` | มีเฉพาะเว็บ |

### 3.7 โทเคนที่มีเฉพาะหน้า `/analyze`

หน้า `/analyze` แยก build เหมือนเว็บแอป แต่**ใช้ชื่อโทเคนของคู่มือ** เพราะเป็นเครื่องมืออ่านลักษณะเอกสาร
ไม่ใช่แอปที่มีงานหลายหน้า — ถ้าใช้ชื่อ `--brand`/`--ink` จะสับสนกับคู่มือในไฟล์เดียวกัน

| โทเคน | สว่าง | มืด | ใช้ทำอะไร |
|---|---|---|---|
| `--on-accent` | `#ffffff` | `#0f231d` | ตัวอักษรที่วาง**บนพื้น `--accent`** |

> ⚠️ `--on-accent` มีหน้าที่เหมือน `--on-brand` ของเว็บแอปทุกประการ (ข้อ 3.6)
>   ปุ่ม “วิเคราะห์ด้วย AI” ใช้พื้น `--accent` ตัวอักษรต้องสลับขั้วตามโหมด
>   ถ้าเขียน `color: #fff` ตายตัว ตอนโหมดมืดจะอ่านไม่ออก **โดยไม่มี error**

หน้า `/analyze` มีโทเคนสถานะครบชุด (`--ok-bg` `--ok-line` `--warn-bg` `--warn-line`
`--danger-bg` `--danger-line`) เพราะหน้านี้แสดงผลตามระดับความรุนแรงของเหตุการณ์จริง ๆ
(เหตุการณ์กระจายหลายจุด = `--warn` เหตุการณ์จุดเดียว = `--text-dim`) — คู่มือกับเว็บแอปที่มีโทเคนชุดนี้เช่นกัน

ตัวที่ตกและต้นตอ — ทั้งหมดแก้โดย**ย้ายพื้น หรือเปลี่ยนโทเคน** ไม่ใช่ลดความเข้มของสี

### 4.6 บั๊กที่เกณฑ์เดิมจับไม่ได้เลย — โค้ด JS หลุดนอก `<script>`

เจอจากภาพหน้าจอผู้ใช้ 7 ตุลาคม 2026 บล็อกโค้ดสลับโหมดหลุดออกมานอก `<script>`
**เบราว์เซอร์แสดงโค้ดเป็นข้อความธรรมดาบนหน้า** ผู้ใช้เห็นบรรทัด `function current() { var set = root.getAttribute('data-theme')…`

| ช่องที่ทำให้รอด | อาการ |
|---|---|
| console ของเบราว์เซอร์ | **ไม่มี error** — เพราะ JS ที่หลุดไม่ได้ถูกรัน แต่กลายเป็น text node |
| `check-style-tokens.mjs` เดิม | **ผ่านทั้งหมด** — เกณฑ์ตรวจแค่สีกับโทเคน ไม่ได้ตรวจโครงสร้าง HTML |
| ปุ่มสลับโหมด | กดไม่ทำงาน เพราะสคริปต์ไม่เคยถูกเรนเดอร์ |

**แก้แล้ว** — ครอบ `<script>` ให้ครบ และเพิ่มเกณฑ์สองชั้น:

1. `check-style-tokens.mjs` — ตัดบล็อก `<style>` และ `<script>` ออก แล้วตรวจว่าส่วนที่เหลือยังมีลายเซ็นโค้ดอยู่ไหม
2. `probe-no-raw-code.mjs` — อ่าน `document.body.innerText` ของหน้าจริง แล้วตรวจลายเซ็น 7 แบบ

> ⚠️ เกณฑ์แรกมี false positive ตอนแรก เพราะตัดแต่ `<script>` ไม่ได้ตัด `<style>`
>   ทำให้แท็ก `<style>` ที่ถูกต้องถูกนับเป็นบั๊ก → ตกตลอดแบบไม่มีสาเหตุ
>   **ต้องตัดทุกอย่างที่เป็นโค้ดออกหมดก่อนตรวจว่ามีโค้ดหลุด**

**บทเรียนที่ใช้ได้กับทุกหน้า** — เกณฑ์ที่ผ่าน ไม่ได้แปลว่าหน้าเว็บใช้งานได้
ถ้าไม่เคยตรวจ "สิ่งที่ผู้ใช้เห็นจริง" เกณฑ์ก็แค่ตรวจว่าไฟล์ตรงตามที่ตัวเองคาดไว้เท่านั้น

## 5 · กฎการใช้สีตามความหมาย

สีในหน้านี้สื่อความหมาย ไม่ใช่แค่ของตกแต่ง — ผู้อ่านไทยจะอ่านเขียวว่า “ถูก” แดงว่า “ผิด” เหลืองว่า “ยังไม่แน่ใจ”
ต้องรักษาความหมายนี้ไว้เสมอ

| สถานการณ์ | โทเคนที่ใช้ | ห้ามใช้แทน |
|---|---|---|
| ลิงก์ที่กดได้ | `--accent` | `--text-dim` (ดูเหมือนข้อความธรรมดา) |
| หัวข้อที่อ่านอยู่ | `--accent` + พื้น `--accent-soft` | ใช้สีอื่นสลับไปมา |
| ผลลัพธ์ถูกต้อง | `--ok` | `--accent` (ถึงจะสีเดียวกันตอนนี้ แต่คนละความหมาย) |
| ผลลัพธ์ผิด / ยังไม่ได้ทำ | `--danger` + พื้น `--danger-soft` | `--warn` |
| ยังไม่ได้ทดสอบ | `--warn` | `--danger` (ทำให้ดูเหมือนผิด) |
| กล่องข้อมูลธรรมดา | `--surface` + ขอบซ้าย `--accent` | ไม่ต้องใช้พื้นสี |
| กล่องเตือนระดับวิกฤต | `--danger-soft` + ขอบซ้าย `--danger` | |

**กฎที่ห้ามละเมิด**

- ห้ามใช้สีเป็นช่องทางเดียวในการสื่อความหมาย — ทุกจุดที่ใช้สีต้องมีข้อความหรือรูปร่างกำกับ
  เช่น ป้าย “ไม่มี” เขียนกำกับด้วย ไม่ใช่แค่แดง
- ห้ามใช้ `--accent` เป็นพื้นของตัวอักษรขนาดใหญ่ เพราะจะอ่านยาก
- ห้ามออกแบบสิ่งที่ “ต้องการความสนใจ” ให้เหมือนข้อความธรรมดา
- ห้ามใช้เงาแทนการเปลี่ยนสีพื้น ถ้าต้องการแยกชั้น — ใช้ `--surface-2` ซึ่งเปลี่ยนตามโหมดถูกต้องกว่า

## 8 · กลไกโหมดมืด

### 8.1 คู่มือ `/docs` — ตามระบบเท่านั้น ไม่มีปุ่มสลับ

ผู้ใช้ตั้งที่ระดับเครื่อง เหตุผลคือคู่มือเป็นหน้าอ่านอย่างเดียว ไม่มีค่าที่ผู้ใช้ตั้งเอง
การมีปุ่มสลับจะเพิ่มสถานะที่ต้องจำ และถ้าผู้ใช้ปิดเครื่องแล้วลืมว่าเคยสลับไว้ หน้าก็จะออกมาไม่ตรงกับที่เลือก

### 8.2 เว็บแอปและหน้า `/analyze` — มีปุ่มสลับ, เพราะผู้ใช้สั่งเพิ่ม

ปุ่มอยู่ใน sidebar ที่เดียวที่ทุกหน้าเว็บแอปใช้ร่วมกัน (`ThemeToggle` ใน `AppRail`)
**ไม่ใช่** ใน pagebar ของแต่ละหน้า — เพราะหน้าที่ลืมใส่จะไม่มีปุ่มเลย
(เกิดแบบเดียวกับที่ปุ่มเปิดเมนูหายไปจาก `/teams` และ `/teams/[id]` เมื่อก่อน)

หน้า `/analyze` เป็นไฟล์ HTML เดี่ยว จึงมีปุ่มอยู่ในแถบ `.pills` ของตัวเอง — ไม่มีโครงสร้างร่วมให้ใช้

**คีย์ localStorage ต้องเป็น `docgen-theme` เดียวกันทั้งสองหน้า**
เพราะผู้ใช้สลับโหมดที่หน้าเว็บแอป แล้วเปิด `/analyze` ต้องเห็นโหมดเดียวกันโดยไม่ต้องกดซ้ำ
ถ้าใช้คีย์แยก (`analyze-theme`) ผู้ใช้จะต้องกดสลับสองครั้งทุกครั้งที่ข้ามหน้า — นั่นคือ "หน้าตาไม่เหมือนกัน"

มีสามสถานะ ไม่ใช่สอง:

| สถานะ | เกิดเมื่อไหร่ | ใครเป็นเจ้าของค่า |
|---|---|---|
| ไม่เคยกด | เปิดครั้งแรก | ระบบ (`prefers-color-scheme`) |
| สั่งสว่าง | ผู้ใช้กดจากโหมดมืด | ผู้ใช้ จำข้ามหน้า |
| สั่งมืด | ผู้ใช้กดจากโหมดสว่าง | ผู้ใช้ จำข้ามหน้า |

### 8.3 โครงสร้าง CSS ที่รองรับสามสถานะ

```css
/* โครงสร้างจริงใน apps/web/app/globals.css — ต้องมีครบทั้งสามช่วง */
:root { /* ค่าโหมดสว่าง — ประกาศครบทุกตัว รวมถึง --on-brand */ }

@media (prefers-color-scheme: dark) {
  /* ⚠️ ต้องมี :not([data-theme='light']) */
  :root:not([data-theme='light']) { /* ค่าโหมดมืด เมื่อผู้ใช้ยังไม่เคยสั่ง */ }
}

/* ผู้ใช้กดเอง */
:root[data-theme='dark'] { /* ค่าโหมดมืด — ต้องตรงกับบล็อกข้างบนทุกตัว */ }
```

**ทำไมต้องเขียนมืดสองบล็อก** — ถ้ารวมเป็นบล็อกเดียว ผู้ใช้ที่อยู่ในระบบมืดจะ**กดสลับออกมาไม่ได้**
เพราะ media query ไม่เคยถูกปิด ค่ามืดจะทับทุกครั้งที่โหลดหน้า
ถ้าไม่แยกบล็อก ผู้ใช้ที่เลือกโหมดสว่างจะเจอหน้าสว่างตอนเปิด แล้วมืดตอนกดปุ่ม → สลับไม่ได้จริง

**ทำไมไม่ใช้ `light-dark()`** — เบราว์เซอร์เก่าไม่รู้จักฟังก์ชันนี้ แล้วจะทิ้ง**ทั้งบรรทัด**ทิ้ง
เหมือนไม่ได้เขียน CSS นั้น → โทเคนหายเงียบ ๆ โดยไม่มี error

**ข้อบังคับสำคัญ**

- ต้องประกาศ**ครบทุกตัวในบล็อกมืด** ถ้าไม่ครบ ตัวที่ลืมจะได้ค่าของโหมดสว่างไปใช้
  เช่น พื้นโหมดสว่างกับข้อความโหมดมืด = อ่านไม่ออก **ไม่มี error**
- **บล็อกมืดสองบล็อกต้องตรงกันทุกค่า** ไม่ใช่แค่จำนวนโทเคนเท่ากัน
  ถ้าไม่ตรง ผู้ใช้ที่กดสลับเองจะเห็นคนละธีมกับตอนเปิดครั้งแรก โดยไม่มี error
- คีย์ใน `localStorage` ต้องเหมือนกันทั้งสคริปต์ตั้งค่าตอนโหลดหน้าและตัวปุ่ม (`docgen-theme`)
  ถ้าไม่ตรง ปุ่มจะจำได้แต่หน้าจะไม่กลับมาเป็นค่าเดิม
- ต้องตั้ง `color-scheme` ของ `<html>` ตามโหมดด้วย ไม่งั้นช่องค้นหา แถบเลื่อน
  และลูกศรของ dropdown ที่เบราว์เซอร์วาดเองจะยังเป็นโทนสว่างทั้งที่หน้าเป็นโหมดมืด
- ค่าที่ผู้ใช้เลือกต้องถูกเขียนลง `<html>` **ก่อนเว็บวาดครั้งแรก** ด้วยสคริปต์สั้น ๆ ใน `<head>`
  ถ้ารอ `useEffect` ใน React ผู้ใช้จะเห็น**กะพริบสีขาว**ทุกครั้งที่เปิดหน้า
  (แก้ด้วย React ไม่ได้ เพราะ `useEffect` รันหลังวาดเสร็จเสมอ)
- ตรวจด้วยตาจริงทั้งสองโหมดทุกครั้ง — ในเบราว์เซอร์ได้จาก DevTools ▸ Rendering ▸ Emulate CSS `prefers-color-scheme`
- สีที่เป็น “น้ำหนักของการอ่าน” ต้องสลับขั้วในทุกโหมด ไม่ใช่แค่ลดความอ่อนลง
- **ห้ามใช้สีเดียวกันทั้งสองโหมดกับพื้น** เช่น `--accent` เขียวเข้มบนพื้นเข้ม = จมหาย

**เกณฑ์ที่ตรวจเรื่องนี้**

| สคริปต์ | ตรวจอะไร |
|---|---|
| `logs/check-style-tokens.mjs` | บล็อกมืดครบทุกตัว · บล็อกมืดสองบล็อกตรงกันทุกค่า · ตั้งธีมก่อนวาดครั้งแรก · ใช้คีย์ `docgen-theme` · มีปุ่มสลับ |
| `logs/prove-style-check.mjs` | ฉีดบั๊ก 6 แบบแล้วต้อง**ตกครบทั้ง 6** — พิสูจน์ว่าเกณฑ์ข้างบนจับบั๊กได้จริง ไม่ใช่ผ่านลวง |
| `logs/probe-analyze-theme.mjs` | เปิดทั้งสองโหมดจริงในเบราว์เซอร์ ตรวจว่าพื้นเปลี่ยนจริง ไม่มีผิวขาวหลุด และคอนทราสต์ผ่านทุกจุดที่มีข้อความ |

> ⚠️ **ผ่านเฉพาะเมื่อเนื้อหาโหลดเสร็จแล้ว**
>   probe รอ `.stat` และ `.grp` ปรากฏก่อนเริ่มวัด ถ้าไม่รอ จะได้แค่ 30 จุดแล้วผ่านลวง
>   ตัวเลข “ผ่าน N จุด” จึงต้องมากพอสมควรด้วย — ถ้าเห็น 30 จุด แปลว่ายังไม่ได้วัดของจริง

## 10 · กติกาการดูแล

1. **เปลี่ยนสีที่โทเคนเท่านั้น** อย่าเขียนสีตรง ๆ ในกฎอื่น
   เพราะสีที่ฝังตรงจะไม่เปลี่ยนตอนสลับโหมด → ตอนมืดจะออกมาเป็นสีผิดโทนเงียบ ๆ
2. **ห้ามเขียนสีใน `style={{ }}` ของ React ด้วย** — เป็นข้อผิดพลาดเดียวกันข้อ 1
   เพราะ inline style แข่งขันกับ CSS ทุกชั้น **ชนะเสมอ** และไม่ถูกโทเคนกำกับ
   เจอจริง: ปุ่มเลขหน้ามี `background: '#fff'` ใน `Pager.tsx` ทำให้แก้ CSS ไปแล้วก็ยังพัง
   (ดูข้อ 4.4)
   **ห้ามเขียนสีใน `style="..."` ของ HTML เช่นกัน** ให้ทำเป็นคลาสแทน
   เจอจริงในหน้า `/analyze`: มีสีฝังใน inline style ถึง 9 จุด ทั้งที่เขียน `var(--token)` ถูกต้องแล้ว
   ก็ยังผิด เพราะถ้าวันหนึ่งต้องการเปลี่ยนค่าผ่าน CSS จะแก้ไม่ทัน
   > เช็คเองได้: `Select-String -Path <ไฟล์> -Pattern 'style="[^"]*(color|background)'` ต้องได้ว่าง
3. **แก้ทั้งสองโหมดพร้อมกันเสมอ** โหมดสว่างค่าเดียวไม่จบ — ต้องไล่ดูอีกโหมดด้วย
4. **เพิ่มตัวแปรใหม่ต้องมีทั้งสองโหมด** และเพิ่มลงตารางข้อ 3.0 พร้อมกัน
   ยกเว้นโทเคนที่ไม่ขึ้นกับโหมด (`--radius` `--font-*`) ประกาศครั้งเดียว
5. **เพิ่มสีใหม่ต้องวัดคอนทราสต์** ก่อน แล้วเพิ่มลงตารางข้อ 4
   เกณฑ์ขั้นต่ำ 4.5:1 สำหรับตัวอักษร และ 3:1 สำหรับเส้นขอบที่สื่อความหมาย
6. **ตรวจทั้งสองโหมดด้วยตาจริง** ก่อนจบ ไม่ใช่ดูแค่สลับค่าในโค้ด
   - ทุกส่วน: `node logs/check-style-tokens.mjs`
   - คอนทราสต์จากเบราว์เซอร์จริง: `node logs/probe-analyze-theme.mjs [url]`
   - ต้องรอให้เนื้อหาโหลดเสร็จ — ดูคำเตือนท้ายข้อ 8.3
7. **ไม่ใช้เงาทำหน้าที่ของสี** ถ้าต้องแยกชั้นให้ใช้ `--surface-2`
   แต่ถ้าวางตัวเลขหรือป้ายสถานะที่มีสี ให้ใช้ `--surface` — ดูข้อ 4.5
8. **ตัวอักษรบนพื้นเน้นต้องสลับขั้ว** ใช้ `--on-brand` (เว็บแอป) หรือ `--on-accent` (`/analyze`)
   ห้ามเขียนขาวตายตัว (ข้อ 3.6 และ 3.7)
9. **แก้โทเคน = แก้ที่สองบล็อกมืดเสมอ** ตามระบบ และผู้ใช้กด (ข้อ 8.3)
   แก้บล็อกเดียวแล้วลืมอีกบล็อก = ผู้ใช้ที่กดปุ่มเห็นคนละธีม โดยไม่มี error
   `check-style-tokens.mjs` จะตกทันที ถ้าค่าไม่ตรงกัน
10. **ปุ่มที่ทุกหน้าต้องมี ต้องอยู่ในชิ้นที่ทุกหน้าใช้ร่วมกัน** ไม่ใช่ใน pagebar ของแต่ละหน้า
   เพราะหน้าที่ลืมใส่จะไม่มีปุ่มเลย โดยไม่มี error (เจอแบบนี้กับปุ่มเปิดเมนูบน `/teams`)
11. **คีย์ localStorage ของธีมต้องเป็นชื่อเดียวกันทุกส่วน** (`docgen-theme`)
   ไม่งั้นผู้ใช้ต้องกดสลับใหม่ทุกครั้งที่ข้ามระหว่างหน้า ซึ่งคือ "หน้าตาไม่เหมือนกัน"
12. **เกณฑ์ใหม่ทุกตัวต้องมี `prove-*.mjs` ยืนยัน** ว่าจับบั๊กได้จริง
   เกณฑ์ที่เขียนด้วย regex มักผ่านทั้งที่จับบล็อกผิดมากกว่าที่คิด — เจอช่องโหว่จริง 2 จุดตอนพิสูจน์
13. **ตรวจ "สิ่งที่ผู้ใช้เห็นจริง" ไม่ใช่แค่ตรวจไฟล์** — อย่างน้อยหนึ่งเกณฑ์ต้องอ่านจาก DOM ที่เรนเดอร์จริง
   ดูข้อ 4.6 — เกณฑ์เดิมผ่านทั้งหมด ทั้งที่หน้าเว็บแสดงโค้ดดิบให้ผู้ใช้เห็น
14. **สคริปต์ที่ฉีดบั๊กลงไฟล์จริง ต้องคืนไฟล์ใน `finally` เสมอ**
   ถ้าสคริปต์พังกลางทาง ไฟล์จะถูกทิ้งไว้ในสถานะที่ฉีดบั๊ก → ผู้ใช้เจอบั๊กจริงบนหน้าเว็บ
   เคยเกิดจริง: ตัวแปรพลาดตัวตอนแก้สคริปต์ → `fail is not defined` → ไฟล์จริงเสียหาย

## 11 · ปุ่มรายงานปัญหา (ผู้ดูแล)

ผู้ใช้เจอปัญหา → กดปุ่มในแถบ URL มุมล่างซ้าย → ระบบแนบหน้าที่เกิด
ข้อผิดพลาดล่าสุด และภาพหน้าจอให้เอง → เข้ากล่องจดหมายของผู้ดูแล

| ชิ้น | ที่อยู่ | หน้าที่ |
|---|---|---|
| ปุ่ม + กล่อง | `components/AppStatus.tsx` · `components/ReportIssue.tsx` | เปิดกล่อง แนบภาพ (วาง `Ctrl+V` / ลากไฟล์) |
| หน้าดูรายงาน | `app/reports/page.tsx` | ผู้ดูแลเท่านั้น · เปลี่ยนสถานะ · เปิดดูภาพ |
| API | `modules/reports/` | เก็บลง Mongo (`issue_reports`) + ภาพลง S3 + ส่งกระดิ่ง |
| ผู้รับ | `REPORT_TO_SUBS` ใน `dokploy-infra/.env` | คั่นด้วย `,` · **เว้นว่าง = ปิดทั้งฟีเจอร์** |

1. **ห้ามใส่ JSON Schema ดิบลงใน `response:` ของ Fastify** — ต้องเป็น Zod
   เพราะใช้ `@fastify/type-provider-zod` ถ้าใส่ JSON Schema ระบบจะตอบ 500
   **หลังบันทึกข้อมูลและส่งกระดิ่งเสร็จแล้ว** ผู้ใช้เห็น "ส่งไม่สำเร็จ" ทั้งที่รายงานเข้าแล้ว
2. **ตรวจฟิลด์เองด้วย `safeParse` + `ValidationError` ไม่ใช่ `parse()`**
   `ZodError` มี `.issues` แต่ไม่มี `.validation` → error handler กลางจับไม่ได้ → 500 แทน 422
3. **ห้ามเชื่อ `Content-Type` ที่ client ส่งมา** ต้องดูไบต์จริง (`sniffImage`)
   ภาพนี้ถูกส่งกลับมาแสดงบนโดเมนเรา ถ้าเชื่อ mimetype จะเป็น stored XSS
4. **ผู้ดูแลต้องให้ฝั่งเซิร์ฟเวอร์เป็นผู้ตัดสิน** ห้ามให้หน้าเว็บเดาเอง
   ใช้ `GET /api/session` → `canReceiveReports` ยิงครั้งเดียวตอน mount
   แล้วกระจายผ่าน `useCanReceiveReports()` ไม่ใช่แต่ละจุดยิงเอง
5. **ห้ามจำกัดผู้ส่ง** ปุ่มรายงานเปิดให้ผู้ใช้ที่ล็อกอินทุกคน จำกัดแค่ผู้อ่าน
   เพราะการจำกัดผู้ส่งทำให้ปัญหาจริงถูกเก็บเงียบ ๆ
6. **ห้ามใช้ `useSearchParams()` ในหน้าที่ prerender ได้** โดยไม่ห่อ `<Suspense>`
   build จะพัง — อ่าน `window.location.search` ใน `useEffect` แทน ถ้าใช้แค่ตอน mount
7. **กล่องที่ทับทั้งหน้า ต้อง z-index สูงกว่าสิ่งที่เปิดมัน**
   `.report-issue__scrim` = 2147483100 สูงกว่า `.veil` (2147482000)
   เพราะเปิดจากแถบ URL ที่ถูกกางไว้แล้วตอนกด
8. **สี "ไม่มี" ใช้โทเคนที่มีอยู่จริง** `--err` / `--ok` ไม่ใช่ `--danger` ที่ไม่ได้นิยาม
   ตัวแปรที่ไม่มี → declaration ทิ้งทั้งบรรทัด → พื้นหลังโปร่งใส โดยไม่มี error

# ผลการตรวจอัตโนมัติ

โฟลเดอร์นี้ถูก **bind mount** เข้า container `log-watch` ที่ path `/findings`
`log-watch` ทำงานทุกชั่วโมง แล้วเขียนไฟล์ตรงนี้ **เฉพาะเมื่อพบความผิดปกติ**

> โฟลเดอร์นี้ gitignored — เป็นข้อมูลรันจริง ไม่ใช่ซอร์สโค้ด
> อย่าลบ เพราะเป็นบันทึกปัญหาที่ค้างรอให้กลับมาแก้

## ไฟล์ที่จะเจอ

| ไฟล์ | เกิดเมื่อ | อ่านยังไง |
|---|---|---|
| **`latest.md`** | พบปัญหารอบล่าสุด | เปิดอ่านก่อนเสมอ — คือรายงานรอบที่เพิ่งเกิด |
| `YYYY-MM-DD.md` | พบปัญหาในวันนั้น | หลายรอบต่อวันจะถูก**ต่อท้าย**ไว้ในไฟล์เดียว เรียงตามเวลา |
| `runs.jsonl` | **ทุกรอบ ไม่ว่าจะพบปัญหา** | หนึ่งบรรทัด JSON ต่อรอบ ใช้ดูแนวโน้มย้อนหลัง |
| `host-state.json` | ทุก 10 นาที โดย Task Scheduler | ข้อมูลพอร์ตฝั่ง host — เขียนโดยสคริปต์ฝั่ง host ไม่ใช่ watcher |

> เวลาผ่านไปสักพักแล้วไม่มีไฟล์เกิด = ระบบไม่พบปัญหาในรอบนั้น ๆ
> ดู `runs.jsonl` เพื่อยืนยันว่าตัว watcher ยังทำงานอยู่จริง

## รายงานหน้าตาเป็นอย่างไร

```
# พบความผิดปกติ — <วันเวลา>

## สิ่งที่พบ              ← รายการปัญหาแบบสั้น
## สรุปจาก AI            ← สาเหตุที่น่าจะเป็น + สิ่งที่ต้องทำ + ข้อควรระวัง
## ข้อมูลดิบ              ← ตัวเลขทั้งหมดที่ใช้ตัดสิน
```

## watcher เช็คอะไร

| หมวด | วิธี | แหล่งข้อมูล |
|---|---|---|
| สุขภาพระบบ | `/api/health` — ดูราย service (MongoDB · NATS · RustFS · docserver · worker …) | ยิงสด |
| เส้นทางหลัก | ยิง 7 เส้นทางผ่าน gateway แล้วตรวจว่าได้**เนื้อหา** ที่คาด ไม่ใช่แค่ 200 | ยิงสด |
| พอร์ตที่รั่ว | อ่าน `host-state.json` — ดูว่าพอร์ตของเราผูกกับ `0.0.0.0` หรือเปล่า | **ฝั่ง host** |
| เหตุการณ์น่าสงสัย | นับจาก Loki แยกราย container แล้วเทียบกับเกณฑ์ | **Loki** |
| log-analyzer | ต่อได้และติดต่อ Loki ได้ไหม | ยิงสด |

## ทำไมต้องใช้ข้อมูลจาก 3 ที่

ไม่ใช่การอ่านซ้ำซ้อน แต่เป็นคนละชนิดข้อมูลกัน:

| แหล่ง | เก็บอะไร | ทำไม Loki ไม่พอ |
|---|---|---|
| Loki | stdout/stderr ของทุก container | ✅ ใช้แทนการไล่ดู log ทีละที่แล้ว |
| `host-state.json` | พอร์ตที่ host กำลังฟังอยู่ | **Loki เก็บไม่ได้** — ดูหลักฐานด้านล่าง |
| `/api/health` + ยิงเส้นทาง | พฤติกรรมจริงของบริการ | log บอกได้แค่ "เขียนอะไร" ไม่ได้บอกว่า "ตอบได้ไหม" |

### หลักฐานว่า Loki เก็บสถานะพอร์ตของ host ไม่ได้

วัดเมื่อ 2026-10-06 จาก Loki โดยตรง:

```
container ที่มีใน Loki 24 ชม. : 20 ตัว (ครบทุกตัวที่กำลังรัน)
label ที่มีทั้งหมด          : compose_project, container, job, service, service_name, source
label เกี่ยวกับพอร์ต/เครือข่าย : ไม่มีแม้แต่ตัวเดียว
บรรทัดที่บอกว่ากำลังฟังพอร์ต   : listen → 0 · bound to → 0
```

ขณะเดียวกัน host มีพอร์ตเปิดออก LAN อยู่ 19 พอร์ต ซึ่ง Loki **ไม่มีบรรทัดไหนกล่าวถึงเลย**
เหตุผล: Alloy มีแหล่งข้อมูลเดียวคือ `loki.source.docker` = stdout/stderr ของ container
ส่วนสถานะพอร์ตเป็นสถานะของ kernel บน host ซึ่งไม่มี container ไหนเขียนมันลง log ได้

### ทำไมถึงต้องมีสคริปต์ฝั่ง host

ทางที่ดูเหมือนใช้ได้ — ต่อ TCP ไปที่ `host.docker.internal:<port>` แล้วดูว่าต่อได้ไหม
**ผิดบน Windows Docker Desktop (WSL2)** วัดแล้วว่า:

```
พอร์ตที่ผูกกับ 127.0.0.1 เท่านั้น (8090 · 3000 · 4001 · 3100 · 12345)
→ ต่อถึงจาก container ได้หมด  → ขึ้นว่า "รั่ว 5 พอร์ต" ทั้งที่ LAN เข้าไม่ได้จริง
```

เพราะ vpnkit/HNS ใน WSL2 รับการเชื่อมต่อจาก container แล้วส่งต่อเข้า loopback ให้
ถ้าปล่อยไว้แบบนั้น watcher จะร้องเตือนทุกชั่วโมงจนผู้ใช้เลิกสนใจ ซึ่งแย่กว่าไม่ตรวจเลย

## ข้อจำกัดที่ต้องรู้

### ตรวจพอร์ตเฉพาะที่อยู่ในรายการ

`collect-host-state.ps1` ตรวจพอร์ตฝั่ง host เฉพาะรายการนี้:

```
80 · 3000 · 4000 · 4001 · 3100 · 8080 · 8090 · 12345 · 27017 · 4222 · 6379 · 16379 · 9000
```

**ทำไมไม่ตรวจทั้งหมด** — วัดแล้วว่าเครื่องนี้มีพอร์ตที่ผูกกับ LAN อยู่ 19 พอร์ต
เป็น Windows RPC (49664-49668) · SMB (135/139/445) · Tailscale (443/8443) และอื่น ๆ
**ไม่มีพอร์ตไหนเป็นของเราเลย** ถ้าตรวจทั้งหมดจะได้แจ้งเตือนปลอม 19 รายการทุกชั่วโมง

ผลคือ **process บน host ที่ฟังพอร์ตนอกรายการนี้จะไม่ถูกจับ** เช่นทดสอบด้วยพอร์ต 9999 แล้วไม่โดน
แต่ **container ที่ publish พอร์ตออกมาไม่มีข้อจำกัดนี้** เพราะตรวจจาก `docker ps` ทั้งหมด
(โดยเฉพาะ `teable-postgres` 5432 และ `teable-cache` 6379 ที่เปิด `0.0.0.0` อยู่ — เป็นของโปรเจกต์อื่น)

### log ของ container ที่ลบแล้วยังอยู่ใน Loki

Loki เก็บ log ไว้ 14 วัน แม้ container ถูก `docker rm` ไปแล้ว
ถ้าไม่กันไว้ ทุกครั้งที่ลบ container จะมีแจ้งเตือนปลอมซ้ำเป็นเวลา 14 วัน
(เจอจริงระหว่างทดสอบ — container ที่ฉีดเพื่อพิสูจน์วิธีนับ โดนนับเป็น "ปัญหา" 42 ครั้ง/ชม.)

แก้ไว้ 2 ชั้น:

1. **ทิ้งจุดที่เก่ากว่าหน้าต่างที่ถาม** — Loki ไม่คืนจุดใหม่ให้ stream ที่หยุดเขียน
   วัดได้: container ที่หยุดเขียนตั้งแต่ 04:45 ตอนถามเวลา 06:00 ได้จุดเดียวคือ [04:00–05:00]
   ถ้าอ่านจุดสุดท้ายตรง ๆ จะได้ตัวเลขเก่า 1 ชั่วโมง และเดินหน้าไปเรื่อย ๆ เป็นเวลา 14 วัน
2. **เทียบรายชื่อ container ที่ยังทำงานอยู่** ใน `host-state.json`
   รายงานว่า "ไม่ได้ทำงานอยู่แล้ว" แทนที่จะเรียกว่าเป็นปัญหา

### ถ้า host-state.json เกิน 2 ชม. watcher จะรายงาน "ตรวจพอร์ตไม่ได้"

เพราะข้อมูลเก่าแล้วยึดยาวกว่าจะเชื่อถือ — เงียบไปดีกว่าผ่านผิด
ดังนั้น **ตัวเก็บข้อมูลฝั่ง host ต้องรันเอง** ดูคำสั่งลงทะเบียนด้านล่าง

## ไม่ตรวจอะไร (และทำไม)

| ไม่ตรวจ | เหตุผล |
|---|---|
| สถานะ `docker ps` จากใน container | ตั้งใจไม่ mount docker.sock — ใช้ `/api/health` ของระบบเราแทน |
| พอร์ตของ process บน host นอกรายการ | ดูหัวข้อ "ข้อจำกัด" ด้านบน |
| `.xlsx` / `.pptx` | ไม่รองรับอยู่แล้ว |
| พฤติกรรมหน้าเว็บ (UI) | ต้องขับเบราว์เซอร์จริง — ทำแยกใน `docgen-platform/tests/` |

## ดูย้อนหลัง

```powershell
# รอบตรวจล่าสุด
Get-Content D:\2docx.com\dokploy-infra\log-watch\findings\latest.md

# ดูว่าตัว watcher ยังทำงานอยู่ไหม (ดูเวลา ts ของบรรทัดสุดท้าย)
Get-Content D:\2docx.com\dokploy-infra\log-watch\findings\runs.jsonl | Select-Object -Last 1

# นับว่าตกปัญหากี่ครั้งใน 7 วัน
Get-Content D:\2docx.com\dokploy-infra\log-watch\findings\runs.jsonl |
  Select-Object -Last 168 | ConvertFrom-Json | Where-Object { -not $_.ok } | Measure-Object
```

## ลงทะเบียนตัวเก็บข้อมูลฝั่ง host (ทำครั้งเดียว)

```powershell
schtasks /Create /TN "2docx-log-watch-collect" `
  /TR 'powershell.exe -NoProfile -ExecutionPolicy Bypass -WindowStyle Hidden -File "D:\2docx.com\dokploy-infra\log-watch\collect-host-state.ps1"' `
  /SC MINUTE /MO 10 /F
```

ตรวจว่าลงไว้แล้ว:

```powershell
schtasks /Query /TN 2docx-log-watch-collect /FO LIST /V | Select-String "Next Run|Last Result"
```

> ⚠️ task นี้ถูกสร้างโดย **ไม่ระบุผู้ใช้** → จะรันเฉพาะตอนผู้ใช้ที่สร้างยังล็อกอินอยู่
> ถ้าเครื่องล็อกอินไว้แล้ว watcher จะรายงาน "ตรวจพอร์ตไม่ได้" ทุกชั่วโมง
> แก้ได้ด้วยการรันผู้ดูแลระบบ (Run as SYSTEM) แต่ต้องมีสิทธิ์ผู้ดูแลระบบ

## ปรับพฤติกรรม

ตั้งค่าได้ใน `docker-compose.yml` ที่ service `log-watch`:

| ตัวแปร | ค่าเริ่มต้น | ความหมาย |
|---|---|---|
| `CHECK_INTERVAL_MIN` | `60` | ตรวจทุกกี่นาที |
| `SUSPECT_LIMIT` | `30` | จำนวนบรรทัดน่าสงสัยต่อ container ที่ถือว่าเกิน |
| `WATCH_MODEL` | `minimax/MiniMax-M3.1-Flash-Preview` | โมเดลที่ใช้สรุป |

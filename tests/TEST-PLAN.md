**ข้อความยาว** — ⚠️ **นี่คือข้อจำกัดสำคัญ**

| ขนาดข้อความ | เวลา | หน้า | ผล |

| 100 KB | 60+ วิ | — | ไม่ผ่าน |

### ส่วนที่ 8: เอกสารจริงครบวงจร
รวมทุกอย่างเข้าด้วยกันตามขั้นตอนจริง

```
รับข้อมูล JSON + รูป
    ↓
ฉีดรูปลงแม่แบบ (ตัวฉีดของเรา)
    ↓
ส่งเข้า Carbone เติมข้อความ
    ↓
แปลงเป็น PDF
    ↓
ตรวจสอบผลลัพธ์
```

ทดสอบหนังสือราชการครบทุกส่วน ทั้งชุดที่เร่งด่วนและไม่เร่งด่วน และยืนยันว่าผลลัพธ์ต่างกันจริง (ไม่ใช่ไฟล์ค้าง)

**ผลจริง:** 40/40 ผ่าน · ใช้เวลา 0.4 วินาที

#### ⚠️ ลำดับขั้นตอนที่ถูกต้อง (สำคัญมาก)

```
1. ส่งแม่แบบเข้า Carbone เติมข้อความ  →  ได้ DOCX
2. ฉีดรูปลงไฟล์ DOCX ที่เติมข้อความแล้ว
3. ส่งไฟล์นั้นกลับเข้า Carbone แปลงเป็น PDF
```

**ห้ามสลับลำดับ** ถ้าฉีดรูปก่อนแล้วค่อยเติมข้อความ
ระบบจะเติมไม่ได้ เพราะแท็กที่เหลืออยู่ในไฟล์เดียวกับ XML ของรูป

> ที่ผิดครั้งแรก: ฉีดรูป → แล้วเติมข้อความ → ได้ PDF ที่ยังมีแท็ก `{d.xxx}` ค้างอยู่ทั้งฉบับ
> ตรวจพบเพราะเปิดดูภาพผลลัพธ์ ไม่ใช่ดูจากตัวเลขที่ผ่านหมด

#### บั๊กที่เจอและแก้ในตัวฉีดรูป

**อาการ:** หลายรูปในช่องตาราง กลายเป็นซ้อนกันทั้งหมด
**สาเหตุ:** รูปทั้งหมดถูกวางในย่อหน้าเดียวกัน ช่องตารางจึงไม่จัดบรรทัด
**วิธีแก้:** ตรวจว่าอยู่ในตารางหรือไม่ ถ้าอยู่ให้สร้างย่อหน้าใหม่ต่อกัน (นอกตารางยังเรียงแนวนอนเหมือนเดิม)

## ข้อค้นพบระหว่างทดสอบ

### 0. ⚠️ ลำดับ: ต้องเติมข้อความก่อนฉีดรูป

**สำคัญที่สุดของทั้งโปรเจกต์**

```
ถูก:  แม่แบบ → Carbone เติมข้อความ → ฉีดรูป → Carbone แปลง PDF
ผิด:  แม่แบบ → ฉีดรูป → Carbone เติมข้อความ (ไม่สำเร็จ)
```

เหตุผล: การฉีดรูปเขียนทับ XML ภายในไฟล์ docx ซึ่งเป็นไฟล์เดียวกับที่เก็บข้อความ
ผลคือแท็กที่เหลืออยู่ถูกรบกวนจน Carbone มองไม่เห็น

### 1. ไวยากรณ์ Carbone ที่ใช้ได้จริง

| ต้องการ | ใช้ได้ | ใช้ไม่ได้ |
|---|---|---|
| ตัวแปรเดี่ยว | `{d.ชื่อฟิลด์}` | `{ชื่อฟิลด์}` (ลืม `d.`) |
| ตารางซ้ำ | `{d.items[i].ชื่อ}` + `{d.items[i+1]}` | `{#d.items}...{/d.items}` |
| เงื่อนไข | `{d.ฟิลด์:ifEQ(ค่า):show('ข้อความ')}` | `{#d.เงื่อนไข}...{/d.เงื่อนไข}` |
| แปลงไฟล์ | `"convertTo": "pdf"` | `"format": "pdf"` |

### 2. ตารางซ้อน 2 ชั้น ต้องมี `[i+1]` ของทุกชั้น

**อาการ:** แม่แบบซ้อน 2 ชั้น แต่มีแต่ `[i+1]` ของชั้นนอก
**ผลลัพธ์:** ระบบตอบ error

```
The marker {d.กลุ่ม[i].รายการ[i].ชื่อ} has no corresponding [i+1]
for array "รายการ".
```

**วิธีแก้:** ต้องมี 4 แถว — หัวตาราง / ข้อมูลเปิดทั้งสองชั้น / ปิดชั้นใน / ปิดชั้นนอก

### 3. ตัวฉีดรูป: ต้องสร้างส่วนรูปแยกทุกอัน

**อาการ:** แทรก 3 รูปในช่องเดียว แต่ทุกรูปแสดงเป็นรูปเดียวกัน
**สาเหตุ:** python-docx เก็บรูปเป็นส่วนร่วมของไฟล์ เขียนทับ `_blob` แล้วทุกรูปชี้ไฟล์เดียวกัน
**วิธีแก้:** สร้าง `ImagePart` ใหม่แยกชิ้น พร้อมตั้งชื่อกันชน และปรับ `a:ext` ไม่ให้รูปบิด

### 4. ⚠️ Community Edition ไม่ตรวจ API Key

**ข้อค้นพบสำคัญ:** ส่ง API Key ผิด หรือไม่ส่งเลย ระบบก็ยังทำงานปกติ
เอกสารระบุว่าจะได้ 401 แต่จริง ๆ ได้ 200

**ผลกระทบ:** ห้ามเปิด Carbone ออกสู่ภายนอกโดยตรง
ต้องสร้าง API Gateway ของเราขึ้นมาคุมสิทธิ์เอง

### 5. `convertTo` ขึ้นกับชนิดไฟล์ต้นทาง

- แม่แบบ `.docx` (document) → `pdf`, `docx`, `odt`, `html`, `txt`, `md`, `epub`
- แม่แบบ `.xlsx` (spreadsheet) → `pdf`, `xlsx`, `ods`, `csv`
- ถ้าใช้ผิด → ได้ error `can't be converted` (ถูกต้อง)

### 6. การตรวจข้อความไทยในไฟล์ Word ต้องตัดช่องว่าง

Word เก็บสระภาษาไทยเป็นหลายส่วน ทำให้การค้นข้อความต่อเนื่องไม่เจอ
ต้องใช้ `helper.contains_ns()` ที่ตัดช่องว่างทั้งสองฝั่ง
มิฉะนั้นจะรายงานผลผิดพลาด (พบจริงระหว่างพัฒนา)

### 7. ⚠️ LibreOffice มีเวลาจำกัด 60 วินาที

**ข้อค้นพบสำคัญของการทดสอบรอบนี้**

วัดได้แน่นอนแล้วว่า ระบบหยุดที่ **60.0 วินาที** พอดี และได้ error `w101`:
```
Time limit reached during DOCX to PDF conversion with LibreOffice (max 60000 ms)
```

**สิ่งที่พบเพิ่มเติม (ทดสอบเจาะลงไป):**

| ประเด็น | ผล |
|---|---|
| เอกสารหนักทำให้ระบบค้างต่อไหม | **ไม่ค้าง** — ทดสอบแล้วผ่าน 4/4 (L) และ 3/3 (ICE) |
| RAM รั่วไหม | **ไม่รั่ว** — คงที่ 373-389 MB ทั้งก่อนและหลัง |
| Carbone ICE เร็วกว่าจริงไหม | **ไม่** — ช้ากว่า LibreOffice ในเอกสารไทยของเรา |
| โหมด async ได้เวลานานกว่าไหม | **ได้ 5 นาที** (ต้องมี webhook) |

**ขอบเขตที่วัดได้จริง:**

| เนื้อหา | เวลา | ผล |
|---|---|---|
| ตาราง 1,000 แถว (36 หน้า) | 1.4 วิ | ผ่าน |

| ข้อความ 60 KB (71 หน้า) | 44.5 วิ | ผ่าน (ใกล้ขีดจำกัด) |
| ข้อความ 100 KB | 60+ วิ | ไม่ผ่าน |

**แนวทางรับมือ:**

| เงื่อนไข | คำแนะนำ |
|---|---|
| หนังสือราชการ / ใบรับเรียน | ใช้ปกติ ไม่ต้องทำอะไร |
| ตารางซ้ำหลายพันแถว | ไม่มีปัญหา 1,000 แถวใช้ 1.4 วิ |
| เอกสารยาว 50-65 หน้า | ใช้โหมด async (5 นาที) |
| เอกสารยาวเกิน 65 หน้า | แบ่งเป็นหลายฉบับ |

## ยังไม่ได้ทดสอบ

| หัวข้อ | เหตุผล | ต้องการเมื่อไหร่ |
|---|---|---|
| **TH Sarabun PSK** (ชื่อฟอนต์เก่า) | ติดตั้งแค่ TH Sarabun New | ถ้าเอกสารราชการเดิมใช้ชื่อ PSK |
| **แม่แบบ .xlsx (Excel)** | ทดสอบแค่ document | ถ้าต้องกรอกข้อมูลลง Excel |
| **แม่แบบ .pptx** | ยังไม่ต้องใช้ | ถ้าต้องทำสไลด์ |
| **ตราสัญลักษณ์ PNG โปร่งใส** | ทดสอบแค่ JPG | แนะนำให้ทำก่อนใช้จริง |
| **ตารางข้ามหน้า** | ยังไม่ทดสอบหัวกระดาษซ้ำ | ถ้าเอกสารยาวหลายหน้า |
| **เลขหน้าอัตโนมัติ** | ใส่ในแม่แบบต้องทำเอง | ถ้าเอกสารยาว |
| **เรียกขนานพร้อมกัน** | ทดสอบทีละคำขอ | ถ้ามีระบบเรียกพร้อมกันเยอะ |
| **ความปลอดภัยชั้น API Gateway** | ยังไม่ได้สร้าง | ก่อนเปิดใช้จริง |

## สิ่งที่ต้องทำก่อนใช้จริง

1. **สร้าง API Gateway** — คุมสิทธิ์เอง เพราะ Carbone ไม่ตรวจ API Key
2. **เติมฟอนต์ TH Sarabun PSK** — ถ้าเอกสารราชการเดิมใช้ชื่อนี้
   วิธี: วางไฟล์ `.ttf` ลง `lib/fonts/` แล้วสร้าง image ใหม่
3. **เตรียมตราสัญลักษณ์เป็น PNG โปร่งใส** — จะได้ไม่มีกรอบสีขาว
4. **ทดสอบกับเอกสารจริง 3-5 ฉบับ** — เพื่อดูว่าตำแหน่งเลขหน้า
   และหัวกระดาษตรงกับที่กำหนดหรือไม่
5. **ตั้งระบบลบไฟล์ชั่วคราว** — ไม่ให้ดิสก์เต็ม

## วิธีแก้ปัญหาเมื่อทดสอบไม่ผ่าน

| อาการ | วิธีตรวจ |
|---|---|
| ส่วนที่ 1 ไม่ผ่าน | เปิด Docker Desktop แล้วรัน `docker start carbone-thai` |
| ข้อความไทยเพี้ยน | ตรวจว่ามีฟอนต์ TH Sarabun ใน container |
| ตัวแปรไม่ถูกแทน | ตรวจว่ามี `d.` นำหน้าและชื่อฟิลด์ตรงกัน |
| ได้ไฟล์ต้นฉบับแทน PDF | ตรวจ `convertTo` และ header `carbone-version: 5` |
| ได้ JSON `renderId` | ใส่ `?download=true` |
| ตารางซ้ำไม่ทำงาน | ตรวจ `[i]` อยู่ช่องแรก และ `[i+1]` อยู่แถวถัดไป |
| เงื่อนไขไม่ทำงาน | ใช้ `ifEQ` + `show()` ไม่ใช่ `{#d.x}` |
| รูปไม่เปลี่ยน | ตรวจ Alt Text ของรูปตรงกับชื่อช่อง |
| รูปซ้ำเป็นรูปเดียว | เรียก `set_many()` และใช้ตัวฉีดรูปใหม่ |

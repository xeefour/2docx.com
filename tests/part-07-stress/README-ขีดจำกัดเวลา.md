# ผลทดสอบขีดจำกัดเวลา 60 วินาที

**วันที่ทดสอบ:** 29 กันยายน 2569
**ระบบ:** Carbone 5.15.2 Community Edition + LibreOffice 26.2

---

## สรุปสั้น

| ประเด็น | ผล |
|---|---|
| ขีดจำกัดเวลาจริง | **60.0 วินาที** (วัดได้ 60.0 และ 60.3 พอดี) |
| เอกสารหนักทำให้ระบบค้างต่อไหม | **ไม่ค้าง** — ทดสอบแล้วผ่าน 4/4 และ 3/3 |
| RAM รั่วไหม | **ไม่รั่ว** — คงที่ 373-389 MB ทั้งหมด |
| Carbone ICE เร็วกว่าจริงไหม | **ไม่** — ช้ากว่า LibreOffice ในเอกสารภาษาไทยของเรา |
| โหมด async ได้เวลานานกว่าไหม | **ได้** — 5 นาที (ต้องมี webhook) |

---

## ผลทดสอบละเอียด

### 1. เวลาที่ใช้จริง

| เคส | เนื้อหา | ผลลัพธ์ | เวลา | หน้า |
|---|---|---|---|---|
| เล็ก | 200 แถว | L | 0.4 วิ | 8 |
| เล็ก | 200 แถว | I (ICE) | 0.3 วิ | 8 |
| กลาง | 1,000 แถว | L | 1.4 วิ | 36 |
| กลาง | 1,000 แถว | I (ICE) | 0.4 วิ | 36 |
| ข้อความ 30 KB | 200 แถว + ข้อความยาว | L | 7.9 วิ | 40 |
| ข้อความ 30 KB | 200 แถว + ข้อความยาว | I (ICE) | 11.3 วิ | 46 |
| ข้อความ 60 KB | 200 แถว + ข้อความยาว | L | 44.5 วิ | 71 |
| ข้อความ 60 KB | 200 แถว + ข้อความยาว | I (ICE) | **หมดเวลา** | - |
| ข้อความ 100 KB | 200 แถว + ข้อความยาว | L | **หมดเวลา** | - |
| ข้อความ 100 KB | 200 แถว + ข้อความยาว | I (ICE) | **หมดเวลา** | - |

**ข้อสังเกต:** ตารางซ้ำจำนวนมาก**ไม่ใช่ปัญหา** — 1,000 แถวใช้แค่ 1.4 วินาที
ปัญหาอยู่ที่ **ข้อความยาวมากในช่องเดียว**

### 2. หลังหมดเวลา ระบบกู้สถานะไหม

ทดสอบด้วยการยิงเอกสารหนักจนหมดเวลา แล้วกลับมายิงเอกสารปกติ

| Engine | ก่อนหมดเวลา | หลังหมดเวลา | RAM |
|---|---|---|---|
| LibreOffice | ผ่าน 3/3 (0.1 วิ) | **ผ่าน 4/4 (0.1-0.2 วิ)** | 383 → 389 MB |
| Carbone ICE | ผ่าน 2/2 (0.4-0.7 วิ) | **ผ่าน 3/3 (0.4-4.2 วิ)** | คงที่ |

**สรุป: ไม่ค้าง ไม่รั่ว ใช้งานต่อได้ทันที** — เป็นข่าวดีมากสำหรับระบบจริง

## ข้อค้นพบสำคัญ: Carbone ICE ไม่ได้ช่วยเรา

เอกสาร Carbone ระบุว่า Carbone ICE **เร็วกว่า LibreOffice 3-300 เท่า**
แต่ผลการทดสอบของเรา **ไม่เป็นจริง**

| เคส | LibreOffice | Carbone ICE | ผล |
|---|---|---|---|
| 200 แถว | 0.4 วิ | 0.3 วิ | เท่ากัน |
| 1,000 แถว | 1.4 วิ | 0.4 วิ | ICE เร็วกว่า 3 เท่า |
| ข้อความ 30 KB | 7.9 วิ (40 หน้า) | 11.3 วิ (46 หน้า) | **ICE ช้ากว่า และหน้าเพิ่ม** |
| ข้อความ 60 KB | 44.5 วิ (71 หน้า) | หมดเวลา | **ICE แย่กว่า** |

**เหตุผลที่เป็นไปได้:**
- เอกสารราชการไทยใช้ฟอนต์ซับซ้อน (TH Sarabun) ซึ่ง ICE จัดการได้ไม่ดี
- เอกสารมีตารางซ้อน + เงื่อนไข + เลขหน้า ซึ่ง ICE ยังรองรับไม่ครบ
- เอกสาร ICE ระบุเองว่า "accurate for 95% of DOCX documents" และมีข้อจำกัดด้านสมการ

**ข้อสรุป: ใช้ LibreOffice (ค่าเริ่มต้น) ไม่ต้องเปลี่ยนเป็น ICE**

ถ้าอยากลอง ICE ต้องทดสอบกับเอกสารจริงของหน่วยงานก่อนเสมอ
ตั้งเป็นรายแม่แบบได้ด้วยแท็ก `{o.converter=I}` ในไฟล์แม่แบบ

## โหมด async (ได้เวลา 5 นาที)

ตามเอกสาร Carbone รองรับการประมวลผลแบบเบื้องหลัง โดยส่ง header `carbone-webhook-url`
ระบบจะตอบกลับทันที แล้วเรียก webhook เมื่อเสร็จ

**ผลทดสอบ: ระบบรับคำขอได้**
```json
{
  "success": true,
  "message": "A render ID will be sent to your callback URL when the document is generated",
  "data": { "renderId": "" }
}
```

ตอบกลับใน 0.0 วินาที และให้เวลาประมวลผล **5 นาที** แทน 60 วินาที

**ข้อดี:** เอกสารขนาด 60 KB ที่ใช้เวลา 44 วินาที จะทำได้สบายมาก
**ข้อเสีย:** ต้องมีเซิร์ฟเวอร์รับ webhook และระบบเรียกกลับ

## เกณฑ์สำหรับระบบจริง

### ตัดสินใจแบบนี้

| เงื่อนไข | คำแนะนำ |
|---|---|
| เอกสารราชการทั่วไป (หนังสือ, ใบรับเรียน) | ใช้ปกติ ไม่ต้องทำอะไร |
| ตารางซ้ำหลายพันแถว | ไม่มีปัญหา 1,000 แถวใช้ 1.4 วิ |
| เอกสารยาวเกิน ~50 หน้า | ใช้โหมด async (5 นาที) |
| เอกสารยาวเกิน 65 หน้า | แบ่งเป็นหลายฉบับ แล้วรวม PDF |

### เกณฑ์ความปลอดภัย

จากข้อมูลที่วัดได้ แนะนำให้ระบบจริงตั้งค่า:

| ค่า | แนะนำ | เหตุผล |
|---|---|---|
| จำกัดพร้อมกัน | 2-3 งาน | ป้องกันการแย่งทรัพยากร |
| เวลารอสูงสุด (client) | 300 วินาที | ให้เหนือขีดจำกัด 60 วิ |
| จับ timeout เป็น error | ต้อง | แจ้งผู้ใช้ให้แบ่งงาน |
| ตรวจ RAM | เฝ้าระวัง | ปกติใช้ ~390 MB |

### เรื่องที่พบระหว่างทดสอบ

**ระวัง: งานที่ค้างทำให้งานถัดไปช้าลง**

ตอนทดสอบต่อเนื่องหลายเคสที่หมดเวลา เอกสารปกติ (1,000 แถว) ที่เคยใช้ 1.4 วินาที
กลับหมดเวลาแทน แต่เมื่อทดสอบแยกทีละเคส ใช้เวลา 1.4 วินาทีตามปกติ

แปลว่า **ถ้ามีงานที่ค้างอยู่ งานใหม่จะช้าลงด้วย** แม้ตัวระบบจะไม่ค้างถาวร

**แนวทางแก้:**
- จำกัดจำนวนงานพร้อมกัน
- ใช้ timeout ที่ชัดเจน (เช่น 90 วินาที) แล้วปล่อยให้ระบบคืนทรัพยากร
- ถ้าพบว่าช้าผิดปกติ ให้ restart container

## ข้อแนะนำสำหรับการใช้งานจริง

### แผนที่แนะนำ

```
ระบบต้นทาง
    ↓
[API Gateway ของเรา]   ← คุมสิทธิ์ + จำกัดงานพร้อมกัน + ตัดสินใจว่าจะใช้ async ไหม
    ↓
[Carbone + LibreOffice]
    ↓
เอกสาร PDF
```

**สิ่งที่ Gateway ต้องทำ:**
1. ตรวจ API Key (Carbone ไม่ตรวจให้)
2. จำกัดพร้อมกันไม่เกิน 2-3 งาน
3. ตั้ง client timeout 300 วินาที
4. ถ้าเกิน 60 วินาที ให้ส่งแบบ async แทน
5. ถ้าเกิน 5 นาที ให้แจ้งให้แบ่งเอกสาร

### โค้ดตัวอย่างการตัดสินใจ

```python
def render_document(data, page_estimate=0):
    # เอกสารสั้น: เรียกตรง
    if page_estimate <= 50:
        return call_carbone(data, timeout=90)

    # เอกสารยาว: ใช้ async ได้เวลา 5 นาที
    return call_carbone_async(data, webhook_url=MY_SERVER)
```

## ข้อยังไม่ได้ทดสอบ

- ตั้ง timeout ของ Carbone เป็นค่าอื่น (ไม่พบตัวแปร env สำหรับเรื่องนี้ในเอกสาร)
- โหมด async เต็มรูปแบบ (ต้องมี webhook ที่รับได้จริงและวัดเวลาครบ 5 นาที)
- การทำงานพร้อมกันจริง (2-3 งานพร้อมกัน)
- ผลกระทบเมื่อเอกสารมีรูปจำนวนมาก
- เอกสาร .xlsx / .pptx ขนาดใหญ่

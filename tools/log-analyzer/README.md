# Log Analyzer — UI วิเคราะห์ log ด้วย LLM

เว็บหน้าเดียวสำหรับอ่าน log ของทุก container แล้วให้ AI สรุปว่าระบบมีปัญหาอะไร
**ไม่ต้องอ่าน log เอง** — ออกแบบมาเพื่อคนที่ไม่ค่อยอ่าน log

> ✅ **ตอนนี้รันเป็น service ใน Docker stack แล้ว** (ตั้งแต่ 5 ต.ค. 2026)
> เปิดที่ **http://127.0.0.1:8090/analyze/** ผ่าน gateway ไม่ต้องรัน `start.cmd`
> รายละเอียดการทำเป็น container: [`dokploy-infra/README.md`](../../dokploy-infra/README.md) → หัวข้อ 5

```
เบราว์เซอร์  http://127.0.0.1:8090/analyze/
     │
     └──► server.mjs ─┬─► Loki API     สถานะ container · ปริมาณ log · เหตุการณ์น่าสงสัย
                      └─► MiniMax API  วิเคราะห์ + ถามต่อ   (ยิงตรง ไม่ผ่าน Python)
```

## เริ่มใช้

**วิธีปกติ — ผ่าน gateway**

```
http://127.0.0.1:8090/analyze/
```

เริ่มอัตโนมัติพร้อม stack:

```powershell
cd dokploy-infra
docker compose up -d
```

**วิธีรันบน host ตรง ๆ (ไม่มี Docker)**

```powershell
tools\log-analyzer\start.cmd
```

> ⚠️ ต้องมี Loki + Alloy ทำงานอยู่ก่อน (`cd dokploy-infra; docker compose up -d loki alloy`)
> ถ้า Loki ไม่ทำงาน UI จะขึ้นว่า `loki: ไม่พร้อม`

## ⚠️ ต้องตั้ง MiniMax API key ก่อนถึงจะใช้ปุ่ม "วิเคราะห์ด้วย AI" ได้

**1 ขั้นตอน** — เปิดไฟล์เดียวของทั้งโปรเจกต์ `dokploy-infra/.env` แล้วเพิ่มบรรทัดนี้

```
MINIMAX_API_KEY=<คีย์ของคุณ>
```

แล้ว **รีสตาร์ท** — `docker compose restart log-analyzer` หรือปิด-เปิด `start.cmd` ใหม่

ไฟล์นี้ถูก `.gitignore` ไว้แล้ว คีย์จะไม่หลุดเข้า git

### server อ่านคีย์จากไฟล์ไหน

**ไฟล์เดียวของทั้งโปรเจกต์** — `dokploy-infra/.env` (รวมไฟล์ env ทั้งหมดไว้ที่นี่เมื่อ 2026-10-06)

เหตุผลที่ต้องอยู่ตรงนั้น ไม่ใช่ที่อื่น: `docker compose` อ่าน `${VAR}` จาก `.env`
**ที่อยู่โฟลเดอร์เดียวกับไฟล์ compose** เท่านั้น ย้ายไปที่อื่น = ค่าทั้งหมดกลายเป็นค่าว่าง
และ container จะ crash ตอน boot โดยไม่มี error ชัดเจน

| ที่รัน | คีย์มาจาก |
|---|---|
| เป็น container (ปกติ) | ตัวแปรจาก compose ซึ่ง compose อ่าน `dokploy-infra/.env` |
| รันบน host (`start.cmd`) | อ่าน `dokploy-infra/.env` เอง |

⚠️ **ห้ามสร้าง `.env` ในโฟลเดอร์นี้อีก** — เคยมีและถูกลบไปแล้วตอนรวมไฟล์
ถ้าสร้างใหม่ server จะไม่อ่าน แต่ดูเหมือนว่า "ตั้งคีย์แล้วแต่ใช้ไม่ได้"

ตรวจว่าคีย์อ่านเจอ (พิมพ์แค่ความยาวและ fingerprint ไม่พิมพ์คีย์จริง):

```powershell
node tools\log-analyzer\check-key.mjs
node docgen-platform\logs\check-minimax-key.mjs   # ยิง API จริง — ยืนยันว่า "ใช้ได้" ไม่ใช่แค่ "อ่านเจอ"
```

> อ่านได้ ≠ ใช้ได้ — คีย์ผิด/หมดอายุก็ "อ่านเจอ" เหมือนกัน ต้องยิงจริงจึงจะรู้
> (`/api/status` รายงานแค่ว่าอ่านคีย์เจอ ไม่ได้ยืนยันว่ายิงผ่าน)

รายงานและ dropdown ของหน้านี้ดูแค่ compose project เดียว (ค่าเริ่มต้น `dokploy-infra`)

ต้องตรงกับกฎ `keep` ใน `dokploy-infra/observability/alloy/config.alloy`
ถ้าเปลี่ยนฝั่งเดียวจะเจออาการแบบ UI มีชื่อที่ไม่มี log หรือมองของตัวเองไม่เห็น

> ⚠️ ตัวกรองนี้จำเป็น เพราะ Alloy กรองตั้งแต่ต้นอยู่แล้วแต่มีผลเฉพาะ log ที่เข้ามาหลัง restart
> ส่วน log เก่าที่เก็บไว้แล้วยังอยู่ครบ 14 วัน ถ้าไม่กรองตอนอ่านจะเห็นของโปรเจกต์อื่นปนอยู่

> ⚠️ รายชื่อใน dropdown มาจาก `count_over_time([24h])` ณ เวลาปัจจุบัน
> ตัวที่ไม่เขียน log เลยใน 24 ชม. จะไม่ปรากฏ — ถือว่าถูกต้อง เพราะเลือกไปแล้วรายงานก็ว่าง

พิสูจน์ว่ายังทำงาน: `node docgen-platform/logs/prove-project-scope.mjs`
(เทียบกับ Docker + Loki สองแหล่งอิสระ และเปิด-ปิดตัวกรองเพื่อดูว่าผลเปลี่ยนจริง)

### ถ้าอยากใช้ endpoint อื่น

ค่าเริ่มต้นคือ **Anthropic-compatible API สาธารณะ** ของ MiniMax
(`https://api.minimax.io/anthropic/v1` — ดู
[เอกสาร](https://platform.minimax.io/docs/api-reference/text-anthropic-api))

> ⚠️ ค่า `baseURL` ใน `%USERPROFILE%\.minimax\config.yaml` ชี้ไปที่เกตเวย์ภายใน
> ของ MiniMax Code (`agent.minimax.io/mavis/...`) ซึ่งรับเฉพาะคีย์ของแอปเท่านั้น
> **โค้ดจึงไม่เอาค่านั้นมาใช้** และใช้ค่าเริ่มต้นข้างบนแทน
> ถ้าจำเป็นต้องใช้เกตเวย์อื่น ให้ตั้งเองใน `.env`:
> `MINIMAX_BASE_URL=https://.../v1`

หมายเหตุ: MiniMax Code ตัวเองเรียกโมเดลได้ แต่ credential ของมันอยู่ภายในแอป
**ไม่มี local API ให้สคริปต์ภายนอกเรียก** ต้องมีคีย์ของตัวเองจึงจะเรียกได้

ระหว่างที่ยังไม่ได้ตั้ง key — **ส่วนภาพรวมและเหตุการณ์น่าสงสัยยังใช้ได้ตามปกติ**
(ข้อมูลมาจาก Loki โดยตรง ไม่ต้องใช้ AI) และ UI จะ disable ปุ่ม AI ให้เอง

## ระดับความคิด (effort) — เลือกเองได้

`MiniMax-M3.1-Flash-Preview` (ตัวล่าสุด) **คิดทุกครั้ง** และค่าเริ่มต้นของ API คือระดับสูงสุด
ถ้าไม่กำหนด คำตอบจะช้าและกินโควตา token มากโดยเปล่า ๆ

UI จึงมีตัวเลือก "ระดับความคิด" — โค้ดส่ง `output_config.effort` ให้โมเดล M3.1 เท่านั้น
(โมเดลรุ่นเก่าไม่รู้จักพารามิเตอร์นี้ จึงไม่ส่ง)

| ระดับ | เหมาะกับ | เวลาจริง (digest 1 ชม.) |
|---|---|---|
| `low` | ถามต่อเรื่องเจาะจง | ~4 วินาที |
| `medium` | ตรวจเฉพาะจุด | — |
| **`high`** (ค่าเริ่มต้น) | วิเคราะห์เต็มรูปแบบ | ~90 วินาที |
| `xhigh` / `max` | งานยากมาก | นานกว่านี้อีก |

ตัวเลข token ที่ใช้จริงจะแสดงใต้ผลวิเคราะห์ (`คิดไป N tok · ตอบ M tok`)

> ⚠️ ถ้าโมเดลคิดจนชนเพดาน `max_tokens` API จะตอบ 200 แต่ไม่มีคำตอบ
> โค้ดจะบอกสาเหตุตรง ๆ ว่า "คิดวนจนชนเพดาน" พร้อมตัวเลข token ที่คิดไป
> แก้ได้ด้วยการลดระดับความคิด ตัด digest ให้เล็กลง หรือเปลี่ยนไปใช้ M3 / M2.7 ที่ไม่คิด

## ทำไมตั้ง `max_tokens` สูง (256K)

`max_tokens` คือ **เพดาน ไม่ใช่เป้าหมาย** — โมเดลหยุดเองเมื่อตอบเสร็จ

วัดจริงด้วย prompt เดียวกัน ต่างแค่เพดาน:

| `max_tokens` | ผล | token ที่ใช้จริง |
|---|---|---|
| 32,000 | 200 | 26 |
| 65,536 | 200 | 16 |
| 131,072 | 200 | 19 |
| **262,144** | 200 | 23 |
| 1,048,576 | **400** | — `does not support max tokens > 524288` |

**เพดานจริงของ API = 524,288**

สรุป:
- ตั้งสูงไม่ทำให้โมเดลใช้ token เพิ่ม (ทุกค่าใช้จริงเท่ากันหมด) จึงไม่มีต้นทุน
- ตั้งสูงกันกรณีที่ "เพดาน" กลายเป็นตัวจำกัดงานจริง — ซึ่งเคยทำให้ล้มเหลวจริง
  (max_tokens 8K + digest 85 บรรทัด → คิดจนหมด แต่ API ตอบ 200)
- ตัวกันความเสียหายจริง ๆ คือ **timeout 300 วิ** ไม่ใช่ `max_tokens`
- โค้ด clamp ที่ 524,288 อัตโนมัติ ต่อให้ client ส่งค่าเกินมา

ทดสอบซ้ำได้ด้วย `node tools\log-analyzer\test-maxtokens.mjs`

## หน้าจอมีอะไรบ้าง

| ส่วน | ได้อะไร |
|---|---|
| ตั้งค่า | ช่วงเวลา (15 นาที → 7 วัน) · เลือก container · เลือกโมเดล · **เลือกระดับความคิด** · คำถามเพิ่มเติม |
| ภาพรวม | จำนวน container + ปัญหา · ปริมาณ log/วัน · เหตุการณ์น่าสงสัย · % ที่ตัด noise · สถานะ replica set |
| เหตุการณ์น่าสงสัย | จัดกลุ่มตามประเภท พร้อม**ช่วงเวลา** — บอกได้ว่าเกิดก้อนเดียว (ตอน restart) หรือกระจาย (ปัญหาค้าง) |
| ผลวิเคราะห์จาก AI | สรุปเป็นหัวข้อ: ปัญหาที่ต้องแก้ · ข้อสังเกต · สถานะปกติ · คำสั่งตรวจสอบ |
| ถามต่อ | ถามเจาะจงเรื่องใน log เดิมได้ โดยมีบทสนทนาเดิมเป็นบริบท |

กด **"ปรับรูปแบบที่จับ"** เพื่อแก้ regex ที่ใช้คัดเหตุการณ์น่าสงสัยได้เอง
(RE2 syntax — ค่าเริ่มต้นอยู่ใน `server.mjs` ตัวแปร `SUSPECT`)

### สี่ pill มุมขวาบนอธิบายอะไร

| pill | หมายถึง | ปกติไหม |
|---|---|---|
| `docker: ปกติ` | ตัวนี้คุยกับ Docker daemon ได้ | ❌ **แดงตลอดในโหมด container** — ตั้งใจไม่ mount `docker.sock` (mount = ได้สิทธิ์ root ของ host) |
| `loki: พร้อม` | ติดต่อ Loki ได้ — คือแหล่งข้อมูลหลักของหน้านี้ | ✅ ต้องเป็นเขียว |
| `key: พร้อม` | อ่าน `MINIMAX_API_KEY` ได้ (ปุ่ม AI ใช้ได้) | ✅ ต้องเป็นเขียวถ้าจะใช้ AI |
| `N โมเดล` | อ่านรายชื่อโมเดลได้กี่ตัว | อ่านได้แม้ยังไม่มีคีย์ |

**ผลของ pill `docker` แดง** — มีแค่ 2 หัวข้อใน digest ที่หายไป:
หัวข้อ 1 (สถานะ container) กับหัวข้อ 2 (สถานะ MongoDB replica set)
ส่วนหัวข้อ 3 (ปริมาณ log) · 4 (เหตุการณ์น่าสงสัย) · 5 (สถิติ Alloy) มาจาก
Loki/Alloy ผ่าน HTTP จึงใช้ได้ปกติ

> ถ้าอยากได้หัวข้อ 1-2 คืนมาโดยไม่เปิดสิทธิ์ Docker ให้อ่านไฟล์สถานะที่
> `log-watch` เขียนไว้แล้ว (`dokploy-infra/log-watch/host-state.json`)
> หรือดึงสถานะจาก `/api/health` ของ gateway — ทั้งสองทางไม่ต้อง mount socket

## API

| เมธอด | path | ทำอะไร |
|---|---|---|
| GET | `/api/status` | สถานะ docker / loki / api key / รายชื่อโมเดล |
| GET | `/api/digest?since=1h&containers=mongo-1` | digest ล้วน ๆ **ไม่ใช้ LLM** (เร็ว ~1-3 วิ) |
| POST | `/api/analyze` | วิเคราะห์เต็มรูปแบบ `{since, containers, model, effort?, question?}` |
| POST | `/api/ask` | ถามต่อ `{since, containers, model, effort?, question, history}` |
| POST | `/api/patterns` | เปลี่ยน regex ที่จับเหตุการณ์ `{pattern}` |

`/api/analyze` และ `/api/ask` ตอบกลับ `info` ด้วย — `effort`, `stopReason`,
`outputTokens`, `thinkingTokens` เพื่อให้เห็นว่าโมเดลใช้อะไรไป

## เรื่องความปลอดภัย

- ผูก `127.0.0.1` เท่านั้น — ไม่มี auth และไม่มีไฟล์ขึ้นเว็บ
- แบบ container: **ไม่ publish พอร์ตเลย** เข้าได้ทาง gateway `/analyze` ที่ผูก `127.0.0.1` เท่านั้น
- ไม่ mount `docker.sock` — digest จะขึ้นว่าอ่านสถานะ container ไม่ได้ (ตั้งใจ)
- server อ่าน key จาก `.env` เพื่อยิง API เอง แต่ **ไม่เคยส่ง key ไปยังเบราว์เซอร์**
  — `/api/status` บอกแค่ว่ามีคีย์ไหม / อ่านมาจากไฟล์ไหน ไม่บอกค่าคีย์
- ไม่เขียน config ชั่วคราวลงดิสก์ ไม่มี dependency นอกจากของมาตรฐาน
